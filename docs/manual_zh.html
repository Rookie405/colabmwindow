1. 整体架构

你的 Windows 电脑
win\*.ps1→ colab CLI → Colab VM
A100 80GB / 167GB RAM→ ExLlamaV3 + api_server.py
:8090→ cloudflared → 公网 https://xxx.trycloudflare.com/v1

本地脚本只负责「指挥」：申请机器、上传脚本、远程执行。所有模型相关的工作（下载约 100 GiB 权重、加载、推理）都在 Colab VM 上完成。服务通过 cloudflared 临时隧道暴露为公网地址，并用 API key 保护。

阶段在哪里执行耗时（参考）
申请 / 恢复机器并验证显存本地 restore.py1–3 分钟
安装 ExLlamaV3（预编译 wheel）VM bootstrap.sh约 20 秒
下载模型权重（固定版本）VM bootstrap.sh约 5 分钟
加载模型 + 启动 API + 隧道VM serve.sh2–6 分钟

2. 前提条件

  • Colab Pro / Pro+ 账户，能分配 A100 High-RAM（80GB 显存）。40GB 的标准 A100 无法加载此模型。
  • Windows 10/11，必须使用 PowerShell 7（pwsh）。Windows 自带的 PowerShell 5.1 在编码、外部命令错误处理等方面行为不同，别人的机器上无法保证复现，所以所有脚本都会拒绝在 5.1 下运行。唯一例外是 win\install-pwsh7.ps1，它就是用来安装 PowerShell 7 的。
  • 不需要 WSL 或 Git Bash。
  • 浏览器可以登录你的 Google 账户（首次授权用）。

3. 一次性安装

第 ① 步在 Windows 自带的 PowerShell（5.1）里运行，之后全部在 PowerShell 7 里运行。

cd <repo>            # 本仓库的位置，例如 C:\work\colabmwindow
# ① 安装 PowerShell 7 + collabm 快捷命令，结束时会询问是否立即运行 ②
powershell -ExecutionPolicy Bypass -File win\install-pwsh7.ps1
# ② 以后需要重新配置时，在 PowerShell 7 里单独运行
pwsh -File win\setup.ps1

setup.ps1 会依次：安装 uv → 安装 google-colab-cli 并把 jupyter-kernel-client 固定为 0.9.0 → 触发 Google 登录 → 显示你的 CU 余额（colab usage）。

装完之后打开新的 PowerShell 7 窗口（Windows Terminal 里选 “PowerShell”，不是 “Windows PowerShell”）。用 $PSVersionTable.PSVersion 确认版本是 7.x。

首次授权：终端会打印一个 Google 授权链接。在浏览器打开、同意后，页面会显示一串授权码，把它完整粘贴回终端并回车。

4. 日常使用流程

① 启动

pwsh -File win\up.ps1

成功后会输出：

[up ..] READY in 14 min
  base_url : https://xxxx.trycloudflare.com/v1
  api_key  : sk-collabosm-xxxxxxxxxxxxxxxxxxxx
  model    : qwen3.8-flash-next-exl3
  saved to : .local\endpoint.json

如果已经有一台在跑的机器，up.ps1 会自动接上它，不会再开新机器。脚本可以放心重跑，已完成的步骤会被跳过。

② 测试

pwsh -File win\test.ps1
pwsh -File win\test.ps1 -Prompt "用中文介绍一下你自己" -MaxTokens 300

③ 查看状态

pwsh -File win\status.ps1

会显示：服务器端所有会话（即正在计费的机器）、VM 当前阶段、健康检查、GPU 显存占用、隧道地址。

④ 关机

pwsh -File win\down.ps1

执行后看输出里的 “remaining server-side assignments”，如果还列着机器，说明仍在计费。

5. 启动参数

参数默认说明
-Sessioncollabosm本地会话名
-CacheSize262144KV 缓存总 token 数（所有并发请求共享，需为 256 的倍数）。80GB 卡上限约 90 万–100 万
-CacheQuant4KV 量化位数（2–8）
-CpuCacheGB0第二级 KV 缓存（锁页内存）。设 8 时，被挤出显存的对话恢复只需 0.58 秒，否则要重新 prefill 约 10 秒
-RecurrentCacheGB4Gated-DeltaNet 检查点存储。默认只能覆盖约 7 万 token 的可恢复前缀；长对话建议 20–30
-Ndt4MTP 投机解码深度
-Gcs4096prefill 分块大小，8192 实测最快（首次会有一次 autotune，第二次才是真实速度）
-WaitMin50最长等待分钟数
-KeepAlive关空闲时也保持机器，会持续耗 CU，不建议

推荐的长上下文 / Agent 配置：

pwsh -File win\up.ps1 -CacheSize 524288 -CpuCacheGB 8 -RecurrentCacheGB 24 -Gcs 8192
-CacheSize、-CacheQuant、-Ndt、-CpuCacheGB 都是加载时参数，改了要重新加载模型（2–6 分钟）。尽量一次想好再启动。

6. collabm 交互终端

类似 Claude Code 的命令行对话界面：在 PowerShell 7 里输入 collabm，会自动进入工程文件夹、连上模型，直接用自然语言对话，不需要手写 JSON。

快捷命令已经在第 3 节的 install-pwsh7.ps1 里装好了。建议在 Windows Terminal 设置里把默认配置文件改成 PowerShell 7。

工程文件夹

默认工作区是仓库旁边的 collabm-workspace 文件夹（例：仓库在 C:\work\colabmwindow，工作区就是 C:\work\collabm-workspace）。第一次运行时会从 workspace-template\ 自动创建。collabm 启动后会自动切换到这里。

路径作用
COLLABM.md工程级指令，每次对话都会自动加进系统提示词（类似 CLAUDE.md）。可以直接编辑，也可以在对话里用 /memory 内容 追加
conversations\每次对话保存两个文件：时间戳.md 用来阅读，时间戳.json 用来之后接着聊
.collabm\history.txt输入历史（按上方向键调出）

想讨论的文件放在工作区里，对话中用 @路径 引用；/run 也在这个文件夹里执行。想换别的文件夹：用 collabm --here 以当前目录为工作区，或者设置环境变量 $env:COLLABM_WORKSPACE。

启动命令

命令作用
collabm进入对话；服务没开时会询问是否先启动 A100
collabm --up服务没开时不询问，直接启动
collabm -c接着上一次对话继续
collabm --here以当前目录作为工作区
collabm -p "问题"单次提问，直接输出答案

输入作用

启动要等多久

情况大约耗时
全新机器（下载权重约 5 分钟 + 加载约 6 分半）12–15 分钟
机器还在、服务还在跑1–3 分钟（直接接上）
机器还在、只是重新加载模型约 2–3 分钟

加载阶段会一直显示 stage=loading，属于正常。超过 10 分钟还没变，就查看 serve.log（见第 10 节）。开一次机器就集中用完，是最省时间也最省 CU 的用法。

目前回复是一次性整段显示的，不会逐字输出（服务端还不支持流式）。另外 cloudflared 临时隧道单个回复超过约 100 秒会被切断，所以 /max 不要设得太大：4096 按约 90 tok/s 算大约 45 秒。退出 collabm 不会关掉 A100，要用 collabm-down 关机。

7. 客户端接入

接口兼容 OpenAI：GET /v1/models、POST /v1/chat/completions（支持 stream，但目前是一次性返回全部内容，不是逐字输出）。认证方式为 Authorization: Bearer <api_key>。

环境变量

$e = Get-Content .local\endpoint.json | ConvertFrom-Json
$env:OPENAI_BASE_URL = $e.base_url
$env:OPENAI_API_KEY  = $e.key

Python

from openai import OpenAI
client = OpenAI(base_url="https://xxxx.trycloudflare.com/v1", api_key="sk-collabosm-...")
r = client.chat.completions.create(
    model="qwen3.8-flash-next-exl3",
    messages=[{"role": "user", "content": "你好"}],
    max_tokens=512)
print(r.choices[0].message.content)

curl

curl https://xxxx.trycloudflare.com/v1/chat/completions ^
  -H "Authorization: Bearer sk-collabosm-..." -H "Content-Type: application/json" ^
  -d "{\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}],\"max_tokens\":64}"
隧道地址每次启动都会变。请求是串行处理的（同一时间只跑一个），这是引擎本身的设计。

8. 费用与额度

机型显存 / 内存CU/小时能否运行
A100 High-RAM79.3 GiB / 167 GB约 7.52✅ 可以
A100 标准约 39 GiB / 83 GB约 5.37❌ 不行

可用小时 = CU 余额 ÷ 7.52。例：500 CU ≈ 66 小时；标称的「约 90 小时」通常是按 40GB 标准版的单价算的。

  • 每次全新开机都要重新下载约 100 GiB 权重并加载模型（约 10–15 分钟），这段时间也在计费。一次开机集中干完活最划算。
  • 如果分到 40GB 机器，restore.py 会立刻关掉（约 0.13 CU），直接重跑 up.ps1 即可。
  • Colab 大约 90 分钟无操作会自动回收机器；持续推理算作活动。
  • 随时用 colab usage 查看余额（见第 10 节的环境变量设置）。

9. 故障排查

启动各阶段：状态、耗时和正常表现

up.ps1 等待时会打印进度行，例如 bootstrap running (3 min) stage=weights downloaded=42.1/100.1 GiB。另开一个 PowerShell 7 窗口运行 status.ps1，也能看到当前的 stage。

stage在做什么正常耗时超过多久算异常
probing / runtime检查镜像、安装 ExLlamaV3 wheel约 20–60 秒> 5 分钟
weights从 HF 下载约 100 GiB 权重（27 个文件）。downloaded 数字应该持续增长约 5 分钟（约 380 MB/s）> 15 分钟，或数字几分钟不动
env / bootstrapped安装完成，写入配置几秒—
loading加载模型：约 36 GiB n-gram 表进内存，约 64 GiB 权重进显存，再启动 API 和隧道。这段时间没有进度条，会一直显示 loading全新机器约 6–7 分钟；同一台机器重载（-RestartServer）约 2–3 分钟> 10 分钟
ready url=https://...服务就绪，up.ps1 显示 READY——
ready_no_tunnel服务起来了，但 cloudflared 隧道没拿到地址—重跑 up.ps1 -RestartServer
serve_failed / serve_timeout模型加载失败，或 10 分钟内没通过健康检查—查看 serve.log（见第 10 节）

合计：全新机器 12–15 分钟；机器和服务都还在时 1–3 分钟（直接接上）。

  • 第一次请求会慢一些（要做一次 kernel autotune），之后才是正常速度。
  • 下载过程中偶尔出现 Read timed out (read timeout=10)，是本地查询状态时的网络超时，下一轮会自动重试，不影响下载。
  • 如果看到 Fetching 27 files，说明是一台新机器（之前那台已经被回收或关掉了），要走完整的下载和加载流程。

常见报错

现象原因 / 处理
collabosm needs PowerShell 7 (pwsh)用了 Windows 自带的 PowerShell 5.1。先运行 install-pwsh7.ps1，然后在 PowerShell 7 窗口里用 pwsh 或 collabm* 命令。
ModuleNotFoundError: No module named 'termios'colab CLI 在 Windows 上的已知问题。win\*.ps1 已自动加载 win\compat 里的替身模块。手动使用 colab 前需先设置 PYTHONPATH（见第 10 节）。
AttributeError: module 'jupyter_kernel_client' has no attribute 'JupyterSubprotocol'colab CLI 0.7.2 自带的 jupyter-kernel-client 0.8 版本不对。setup.ps1 / up.ps1 会自动换成 0.9.0。不要运行 uv tool upgrade google-colab-cli，升级后会被还原；万一升级了，重跑 setup.ps1 即可。
probe x/6 did not answer yet新机器内核还在启动时会出现 1–2 次，属于正常。每次重试都会打印 last output，一直失败时根据它判断：是编码错误、认证过期，还是 VM 已被回收。
rc=6：显存不足被关机分到了 40GB 机器，已经自动关掉。直接重跑 up.ps1。
rc=3：too many assignments账户上已有机器在跑。先用 status.ps1 查看，不需要的用 down.ps1 关掉。
CLI 提示 “No active sessions found”，但机器其实还在本地会话记录过期被清掉了，但 VM 还在计费。重跑 up.ps1，会从服务器端重新接回。
bootstrap failed在 VM 上查看 /content/bootstrap.log（见第 10 节）。wheel 装不上多半是镜像的 Python / torch 版本变了，可以试 -Runtime source（会编译，更耗时）。下载卡住可以设置 HF_HUB_DISABLE_XET=1。
serve_failed / serve_timeout查看 /content/serve.log，常见原因是显存不足（CacheSize 设得太大）。
返回 401API key 不对。以 .local\endpoint.json 或 VM 上的 /content/api-key.txt 为准。
第一次请求特别慢首次生成会做一次 kernel autotune，属于正常。
出错退出时机器通常还在计费。暂时修不好就先 down.ps1。

10. 手动操作 VM

在同一个 PowerShell 窗口先设置一次：

$env:PYTHONPATH = "<repo>\win\compat"
$env:PYTHONUTF8 = "1"

然后：

colab sessions                     # 服务器端正在运行（计费）的机器
colab usage                        # CU 余额
"print(open('/content/bootstrap.log').read()[-3000:])" | colab exec -s collabosm
"print(open('/content/serve.log').read()[-3000:])"     | colab exec -s collabosm
"import subprocess;print(subprocess.run('nvidia-smi',shell=True,capture_output=True,text=True).stdout)" | colab exec -s collabosm
colab stop -s collabosm            # 等同于 down.ps1

colab console（交互终端）在 Windows 上不可用，请用 colab exec。
